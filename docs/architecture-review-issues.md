## 一、技术复杂度问题

### 1.1 OAuth2/OIDC 实现复杂

| 属性 | 值 |
|------|-----|
| **风险等级** | 🔴 高 |
| **状态** | ⬜ 待讨论 |

**问题描述**：
跨域 SSO 涉及授权码流程、Token 刷新、Session 同步、登出联动，实现不当会导致安全漏洞或用户体验差。

**影响范围**：
- 所有模块的用户认证
- 用户登录/登出体验
- 安全性

**可能的解决方案**：
1. 使用成熟的开源方案（Keycloak, Auth0, Casdoor）
2. 简化为 Token 传递方案（初期）
3. 自研轻量级 OAuth2 服务

**讨论记录**：
```
[2025-12-25] 决议：采用方案 B（轻量级 Token 传递）

分析过程：
1. 对比了方案 A（完整 OAuth2/OIDC）、B（轻量级 Token）、D（Casdoor 等托管服务）
2. 方案 B 安全性可达到同等水平，前提是正确实现所有安全机制
3. 方案 B 开发周期短（5-8 人天），完全可控
4. 支持第三方 API 接入（API Key + OAuth2 Provider 自研）

实现要点：
- JWT RS256/ES256 签名
- 短期 Token (15min) + Refresh Token 轮换
- Token 绑定（IP/设备指纹）
- 一次性传递码（跨域 SSO）
- 全局中间件强制租户校验
```

### 1.2 API Gateway 成为单点故障

| 属性 | 值 |
|------|-----|
| **风险等级** | 🔴 高 |
| **状态** | ⬜ 待讨论 |

**问题描述**：
所有请求经过 Gateway，一旦故障全局瘫痪；需要高可用部署，增加复杂度。

**影响范围**：
- 全局可用性
- 系统稳定性

**可能的解决方案**：
1. 多实例部署 + 负载均衡
2. 使用云厂商托管网关（AWS API Gateway, 阿里云 API 网关）
3. 客户端直连 + 服务端鉴权（去中心化）

**讨论记录**：
```
[2025-12-25] 决议：采用方案 1（Nginx + 服务端鉴权），不使用独立 API Gateway

分析过程：
1. 传统 API Gateway 存在单点故障风险，需要额外的高可用部署
2. Nginx 极其稳定，多实例部署简单
3. 鉴权逻辑放在服务端，通过共享 NPM 包统一

架构设计：
- Nginx：域名→租户映射、SSL终止、路由转发、负载均衡
- 共享包 @mt5-platform/shared-auth：TenantAuthGuard、RateLimitGuard、LoggingInterceptor
- 各服务：引用共享包，内置鉴权逻辑

优势：
- 简单可靠，Nginx 几乎不会挂
- 少一个服务 = 少一份资源/运维成本
- 服务可独立运行和测试
```

### 1.3 多中间件协调

| 属性 | 值 |
|------|-----|
| **风险等级** | 🟡 中 |
| **状态** | ⬜ 待讨论 |

**问题描述**：
MT4 + MT5 中间件需要保持 API 一致性，但底层协议差异大，Adapter 层可能变得臃肿。

**影响范围**：
- Trading Gateway 复杂度
- 代码维护性
- 功能一致性

**可能的解决方案**：
1. 定义最小公共接口，差异功能单独处理
2. 每个平台独立 API，前端适配
3. 抽象交易领域模型，屏蔽平台差异

**讨论记录**：
```
[2025-12-25] 决议：采用方案 B（最小公共接口 + 平台特定扩展），MVP 只支持 MT5

设计思路：
1. 定义核心接口 CoreTradingOperations（两平台通用）
2. MT5ExtendedOperations 继承核心接口，添加专属功能
3. 上层业务代码检查平台类型，处理功能差异

实施计划：
- MVP：仅实现 MT5Adapter
- V1.0：按客户需求添加 MT4Adapter（核心功能）
- 后续：按需扩展 MT4 功能

优势：
- 清晰的功能边界，不强求一致
- MVP 快速上线，降低复杂度
- 架构预留扩展能力
```

### 1.4 分布式事务

| 属性 | 值 |
|------|-----|
| **风险等级** | 🟡 中 |
| **状态** | ⬜ 待讨论 |

**问题描述**：
跟单交易涉及跨服务器操作（信号源 → 多个跟单者），如何保证一致性？

**示例场景**：
```
信号源交易: MT5-Server-A (成功)
     │
     ├──→ 跟单者1: MT5-Server-B (成功)
     ├──→ 跟单者2: MT4-Server-C (失败 - 余额不足)
     └──→ 跟单者3: MT5-Server-A (成功)

问题: 跟单者2失败了，如何处理？
```

**可能的解决方案**：
1. 最终一致性 + 补偿机制
2. 记录状态，人工介入失败订单
3. 预检查机制（余额、风控规则）

**讨论记录**：
```
[2025-12-25] 决议：采用方案 A+B 组合（预检查 + 最终一致性 + 状态追踪）

核心认知：
- 跟单不需要强一致性，信号源交易已成交不可逆
- 跟单者是"尽力而为"复制，部分失败不影响其他人

实现方案：
1. 预检查（余额、风控、持仓数、品种）- 减少不必要失败
2. 并行执行 - 互不影响
3. 状态追踪（PENDING→EXECUTING→SUCCESS/FAILED/RETRY）
4. 重试机制 - 网络超时自动重试3次，指数退避
5. 用户通知 - 失败时通知跟单者

失败处理：
- 余额不足：通知用户，不重试
- 网络超时：自动重试3次
- 风控限制：通知用户，不重试
- 交易时间外：等待开市后执行
```

## 二、运维复杂度问题

### 2.1 服务数量爆炸

| 属性 | 值 |
|------|-----|
| **风险等级** | 🔴 高 |
| **状态** | ⬜ 待讨论 |

**问题描述**：
基础架构就需要 10+ 服务，加上企业版专属实例，可能达到 50+ 容器。

**服务数量估算**：
```
基础设施:
  - API Gateway (2 实例高可用)
  - Auth Center (2 实例)
  - PostgreSQL (主从)
  - Redis (集群)
  = 8+ 容器

共享服务池:
  - tenant-api (3 实例)
  - copy-api (3 实例)
  - risk-api (3 实例)
  - trading-gateway (3 实例)
  = 12+ 容器

企业版租户 (假设 5 个):
  - 每个租户 4 服务 × 5
  = 20+ 容器

总计: 40+ 容器
```

**可能的解决方案**：
1. 初期简化部署，单实例起步
2. 使用 Kubernetes 自动化管理
3. Serverless 架构（按需扩展）
4. 延迟企业版专属实例功能

**讨论记录**：
```
[2025-12-25] 决议：MVP 最小部署，每个业务模块独立数据存储

架构设计：
┌─────────────────────────────────────────────────────┐
│                    Nginx (1-2)                       │
└─────────────────────────────────────────────────────┘
                         │
      ┌──────────────────┼──────────────────┐
      ▼                  ▼                  ▼
┌───────────┐      ┌───────────┐      ┌───────────┐
│Tenant API │      │ Copy API  │      │Platform API│
│   (1-2)   │      │   (1-2)   │      │    (1)     │
└─────┬─────┘      └─────┬─────┘      └─────┬─────┘
      │                  │                  │
      ▼                  ▼                  ▼
┌───────────┐      ┌───────────┐      ┌───────────┐
│ Tenant DB │      │  Copy DB  │      │Platform DB│
│ + Redis   │      │  + Redis  │      │  + Redis  │
└───────────┘      └───────────┘      └───────────┘

容器数量（MVP）：
- Nginx: 1
- Tenant API: 1 + PostgreSQL: 1 + Redis: 1 = 3
- Copy API: 1 + PostgreSQL: 1 + Redis: 1 = 3
- Platform API: 1 + PostgreSQL: 1 + Redis: 1 = 3
- 总计：10 容器

优势：
- 模块边界清晰，互不影响
- 独立扩展，按需分配资源
- 数据隔离，安全性高
- 故障隔离，单模块问题不影响其他

成本估算（云服务器）：
- 应用服务器 2核4G × 2台 ≈ ¥400/月
- PostgreSQL × 3（可用小规格）≈ ¥600/月
- Redis × 3（可用小规格）≈ ¥300/月
- 总计：约 ¥1300/月
```

### 2.2 域名/证书管理

| 属性 | 值 |
|------|-----|
| **风险等级** | 🟡 中 |
| **状态** | ⬜ 待讨论 |

**问题描述**：
每个租户多个域名，SSL 证书自动签发和续期成为挑战。

**影响范围**：
- 租户域名绑定流程
- 证书过期风险
- 运维工作量

**可能的解决方案**：
1. Let's Encrypt + Certbot 自动化
2. 云厂商证书服务（自动续期）
3. 通配符证书 + 子域名方案
4. 收取域名绑定服务费，覆盖人工成本

**讨论记录**：
```
[2025-12-25] 决议：单域名证书，MVP 手动管理，后续自动化

实施计划：
- MVP：手动使用 Let's Encrypt 签发单域名证书
- V1.0：实现 Certbot 自动签发 + 自动续期
- 企业版：支持租户自定义域名绑定

MVP 操作流程：
1. 新租户入驻时，手动运行 certbot 签发证书
2. 证书有效期 90 天，设置日历提醒续期
3. 续期命令：certbot renew

后续自动化方案：
- cron job: 0 0 * * * certbot renew --quiet
- 或集成到平台管理后台，一键签发
```

## 三、数据一致性问题

### 3.1 跨模块数据同步

| 属性 | 值 |
|------|-----|
| **风险等级** | 🔴 高 |
| **状态** | ⬜ 待讨论 |

**问题描述**：
用户在基础管理创建，需同步到跟单、CRM 等模块。

**示例场景**：
```
Platform Console: 禁用租户 A 的跟单模块
     │
     ├──→ 数据库更新 ✓
     ├──→ 通知 Auth Center 更新 Token 黑名单 ?
     ├──→ 通知 Copy API 拒绝新请求 ?
     ├──→ 已登录用户的 Session 如何处理 ?
     └──→ 正在进行的跟单订阅如何处理 ?
```

**可能的解决方案**：
1. 事件驱动架构（Event Bus / Message Queue）
2. 共享数据库（部分核心表）
3. 定期同步 + 最终一致性
4. 实时 Webhook 通知

**讨论记录**：
```
[2025-12-25] 决议：问题已消除，无需跨模块数据同步

原因：
1. 各模块独立平级，互不调用
2. 用户身份通过 JWT 传递
3. 交易数据直接从中间件获取

唯一需要的同步：租户状态
- 各模块通过 Redis 缓存租户状态（TTL 5分钟）
- Platform API 禁用租户时清除缓存
- 各模块鉴权中间件检查租户状态
```

- 跨模块配置（租户状态/套餐）使用短 TTL（5-10分钟）
- 关键变更时主动清除缓存

缓存 TTL 配置：
- 租户状态：5分钟
- 租户套餐：10分钟
- 中间件配置：5分钟
```

### 3.3 交易数据延迟

2. 跟单任务并行执行
3. 定位非高频跟单，200-500ms 延迟可接受

延迟预期：
- 跟单执行：200-400ms

后续优化方向（如需）：
- 中间件本地化部署
- 优化中间件推送机制
```

## 四、成本与资源问题

|------|-----|

**成本估算**：
```
最小可行架构:
  - 3 台 4核8G (服务) ≈ ¥1500/月
  - 1 台数据库 ≈ ¥800/月
  - 1 台 Redis ≈ ¥400/月
  - 负载均衡 + 带宽 ≈ ¥500/月
  = ¥3200/月 起步

完整架构 (含 5 个企业版租户):

```

**可能的解决方案**：
1. MVP 最小化，逐步扩展
2. 云服务按量付费
3. 预售/众筹覆盖初期成本

[2025-12-25] 决议：目前不考虑成本优化，优先架构清晰度和模块隔离

- 模块完全独立，故障隔离
- 独立扩展，按需调整资源

- 开发测试环境简单，模块可单独运行

当前优先级：
1. 功能实现和产品上线
2. 架构清晰和可维护性
3. 成本优化（后续业务稳定后再考虑）

## 五、安全问题

### 5.1 Token 泄露影响范围

| 属性 | 值 |
|------|-----|
| **风险等级** | 🔴 高 |
| **状态** | ✅ 已决议 |

**问题描述**：
SSO Token 可访问所有模块，一旦泄露影响大。

**影响范围**：
- 用户数据安全
- 交易安全
- 法律合规

**可能的解决方案**：
1. 短期 Token + 刷新机制
2. 模块级别的权限 Scope
3. 敏感操作二次验证
4. 异常行为检测和自动锁定

**讨论记录**：
```
[2025-12-25] 决议：四层防护机制

第1层 - 短期 Token（MVP 必须）：
  • Access Token: 15分钟
  • Refresh Token: 7天，一次性使用，用后轮换

第2层 - Token 绑定（V1.0）：
  • 绑定 User-Agent（设备指纹）
  • 可选绑定 IP（企业版用户）

第3层 - 敏感操作二次验证（MVP 必须）：
  • 交易操作：验证交易密码
  • 设置变更：验证短信/邮箱验证码
  • 资金操作：验证 2FA（V1.0）

第4层 - 异常检测（V1.0）：
  • 同一 Token 多 IP 使用 → 强制重新登录
  • 短时间大量请求 → 限流告警
  • 异地登录提醒
```

### 5.2 租户数据隔离验证

| 属性 | 值 |
|------|-----|
| **风险等级** | 🔴 高 |
| **状态** | ✅ 已决议 |

**问题描述**：
每个 API 都需验证 tenantId，遗漏会导致越权。

**示例场景**：
```
请求: GET /api/v1/accounts/12345
Headers:
  X-Tenant-ID: tenant_A (来自 Gateway 域名解析)
  Authorization: Bearer <tenant_B_user_token>

如果 API 只验证了 Token 有效性，没有核对 Token 中的 tenantId
是否与 X-Tenant-ID 匹配，就会发生越权访问
```

**可能的解决方案**：
1. 全局中间件强制校验
2. 数据库行级安全策略（RLS）
3. 代码审计 + 自动化测试
4. 安全审计日志

**讨论记录**：
```
[2025-12-25] 决议：三层防护机制

第1层 - 全局中间件 TenantAuthGuard（MVP 必须）：
  • JWT tenantId 与请求 tenantId 必须一致
  • 不一致直接返回 401 Unauthorized
  • 所有 API 默认启用，白名单除外

第2层 - 数据库自动注入（MVP 必须）：
  • Prisma 中间件自动给查询添加 tenantId 条件
  • 使用 AsyncLocalStorage 传递租户上下文
  • 避免开发者遗漏 tenantId 条件

第3层 - 自动化测试（MVP 必须）：
  • 每个资源接口必须有租户隔离测试
  • 测试用例：租户A的Token不能访问租户B的资源
  • 返回 404（不泄露资源存在），非 403
```

## 七、业务逻辑问题

### 7.1 跟单延迟

| 属性 | 值 |
|------|-----|
| **风险等级** | 🔴 高 |
| **状态** | ✅ 已决议 |

**问题描述**：
信号 → Gateway → Copy Engine → 多个中间件，延迟可能达到秒级。

**延迟链路分析**：
```
信号源下单 (T+0ms)
  → MT5 Server 成交 (T+50ms)
  → Middleware 推送事件 (T+100ms)
  → Trading Gateway 接收 (T+120ms)
  → Copy Engine 计算跟单 (T+150ms)
  → 批量发送跟单指令 (T+200ms)
  → 各 Middleware 执行 (T+300ms)
  → 各 MT Server 成交 (T+400ms)

总延迟: 400ms+ (市场剧烈波动时可能更长)
```

**可能的解决方案**：
1. 优化每个环节延迟
2. 并行执行跟单指令
3. 本地化部署（减少网络延迟）
4. 接受延迟，定位为"非高频"跟单

**讨论记录**：
```
[2025-12-25] 决议：接受 300-500ms 延迟，定位非高频跟单

优化后的延迟链路：
  信号源下单 (T+0ms)
    → MT5 Server 成交 (T+50ms)
    → Middleware 推送事件 (T+100ms)
    → Copy API 接收 (T+120ms)        ← 去掉 Gateway 层
    → 跟单计算 (T+150ms)
    → 并行发送跟单指令 (T+200ms)     ← 并行执行
    → 各 Middleware 执行 (T+300ms)
    → 各 MT Server 成交 (T+400ms)

产品定位：
  • 面向普通投资者的社区跟单
  • 非高频交易、非算法交易
  • 300-500ms 延迟可接受

后续优化方向（如需）：
  • 中间件本地化部署
  • 优化网络路由
```
