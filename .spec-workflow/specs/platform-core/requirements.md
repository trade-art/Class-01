# 需求文档: 平台核心模块

## 简介

本文档定义 MT5 Middleware SaaS Platform 的核心功能需求。平台核心模块包括：
- 平台管理员认证与授权
- 租户 (Tenant) 全生命周期管理
- 中间件实例管理
- 订阅计划与计费管理

**目标用户**: Platform Admin (平台管理员)

**价值**: 为 SaaS 平台运营商提供完整的多租户管理能力，支持租户入驻、实例分配、订阅计费等核心业务流程。

## 与产品愿景的对齐

本功能支持架构文档 `SAAS_PLATFORM_ARCHITECTURE.md` 中定义的：
- 第1节: 业务模型 - Platform 作为 SaaS 运营商管理 Tenant (B端客户)
- 第4.1节: Platform Admin Console 功能模块
- 第4.1.4节: 计费管理 - 按租户按月收费模式

## 功能需求

### REQ-1: 平台管理员认证

**用户故事:** 作为平台管理员，我希望能够安全登录平台控制台，以便管理租户和实例。

#### 验收标准

1. 当平台管理员提交有效的邮箱和密码时，系统应签发包含 `type: platform_admin` 声明的 JWT 令牌
2. 当平台管理员提交无效凭证时，系统应返回 401 错误，错误码 `AUTH_401_002`
3. 如果平台管理员账号被禁用，系统应返回 403 错误，错误码 `AUTH_403_002`
4. 当 JWT 令牌过期时，系统应要求重新认证
5. 当平台管理员登出时，系统应使会话失效

### REQ-2: 租户增删改查管理

**用户故事:** 作为平台管理员，我希望能够创建、查看、更新和管理租户，以便接入新的 B2B 客户。

#### 验收标准

1. 当平台管理员创建租户时，系统应：
   - 生成唯一的租户 `id` (UUID)
   - 验证 `code` 的唯一性 (用于路由)
   - 设置默认 `status` 为 `active`
   - 设置默认 `plan` 为 `trial`
   - 创建审计记录并设置 `created_at` 时间戳

2. 当平台管理员查看租户列表时，系统应：
   - 支持分页 (page, pageSize)
   - 支持按状态、计划、创建时间范围筛选
   - 支持按编码、名称、联系邮箱搜索
   - 返回总数用于分页显示

3. 当平台管理员更新租户时，系统应：
   - 验证字段约束
   - 更新 `updated_at` 时间戳
   - 创建审计日志条目

4. 当平台管理员变更租户状态时，系统应：
   - 支持状态转换: active ↔ suspended → terminated
   - 如果状态变更为 `suspended`，则通知受影响的租户管理员
   - 如果状态变更为 `terminated`，则安排数据清理

5. 如果租户 `code` 已存在，系统应返回 409 错误，错误码 `TENANT_409_001`

### REQ-3: 租户白标配置

**用户故事:** 作为平台管理员，我希望能够为每个租户配置白标品牌，以便租户可以自定义其控制台外观。

#### 验收标准

1. 当平台管理员更新租户品牌时，系统应：
   - 接受 `display_name` (显示名称)
   - 接受 `logo_url` (Logo URL)
   - 接受 `primary_color` (主题色，十六进制格式)
   - 验证 logo_url 是有效 URL 或 null
   - 验证 primary_color 匹配十六进制格式 (#XXXXXX)

2. 当租户管理控制台加载时，系统应应用租户的品牌配置

### REQ-4: 中间件实例管理

**用户故事:** 作为平台管理员，我希望能够管理中间件实例并将其分配给租户，以便租户可以连接到其 MT5 服务器。

#### 验收标准

1. 当平台管理员创建实例时，系统应：
   - 生成唯一的实例 `id` (UUID)
   - 关联到唯一一个租户 (`tenant_id`)
   - 验证必填字段: `name`, `host`, `port`, `api_key`
   - 设置默认 `status` 为 `offline`
   - 在 `mt5_servers` JSON 字段中存储 MT5 服务器配置

2. 当平台管理员查看实例列表时，系统应：
   - 支持按租户、状态筛选
   - 显示健康状态 (online/offline/maintenance/error)
   - 显示最后健康检查时间戳

3. 当平台管理员将实例分配给租户时，系统应：
   - 验证租户存在且状态为活跃
   - 检查租户的订阅是否允许额外实例 (max_instances 限制)
   - 如果超出限制，则返回 422 错误，错误码 `TENANT_422_002`

4. 当平台管理员更新实例配置时，系统应：
   - 支持更新 MT5 服务器列表
   - 支持更新连接参数
   - 配置变更后触发健康检查

5. 当系统执行健康检查时，系统应：
   - 更新 `last_health_check` 时间戳
   - 更新 `health_data` 中的连接指标
   - 根据健康检查结果更新 `status`

### REQ-5: 订阅计划管理

**用户故事:** 作为平台管理员，我希望能够管理订阅计划和租户订阅，以便实现平台商业化。

#### 验收标准

1. 当平台管理员查看订阅计划时，系统应显示：
   - 计划名称: Trial, Basic, Professional, Enterprise
   - 每月价格
   - 限制: max_instances, max_admins, max_users, max_mt5_servers
   - 支持级别

2. 当平台管理员变更租户订阅时，系统应：
   - 更新租户的 `plan` 字段
   - 根据新计划更新 `max_instances` 和 `max_admins`
   - 如果降级且当前使用量超出新限制，则在应用前发出警告
   - 如果指定则更新 `billing_cycle`

3. 当租户订阅到期时，系统应：
   - 更新租户 `status` 为 `suspended`
   - 向租户 contact_email 发送通知
   - 在终止前允许宽限期 (可配置)

### REQ-6: 账单管理

**用户故事:** 作为平台管理员，我希望能够为租户生成和管理发票，以便跟踪账单和收入。

#### 验收标准

1. 当计费周期结束时，系统应：
   - 生成唯一 `invoice_no` 的发票
   - 根据租户计划计算金额
   - 设置 `period_start`, `period_end`, `due_date`
   - 设置 `status` 为 `pending`

2. 当平台管理员查看发票列表时，系统应：
   - 支持按租户、状态、日期范围筛选
   - 支持按金额、到期日排序
   - 显示逾期指示器

3. 当平台管理员标记发票为已支付时，系统应：
   - 更新 `status` 为 `paid`
   - 记录 `paid_at` 时间戳
   - 如果租户因未付款而被暂停，则恢复 `active` 状态

4. 当发票逾期时，系统应：
   - 更新 `status` 为 `overdue`
   - 向租户 `billing_email` 发送提醒

### REQ-7: 租户管理员账号管理

**用户故事:** 作为平台管理员，我希望能够管理租户管理员账号，以便帮助租户解决账号问题。

#### 验收标准

1. 当平台管理员创建初始租户管理员时，系统应：
   - 创建角色为 `owner` 的管理员
   - 关联到租户 (`tenant_id`)
   - 发送包含临时密码的欢迎邮件
   - 验证邮箱在租户内的唯一性

2. 当平台管理员重置租户管理员密码时，系统应：
   - 生成安全的临时密码
   - 发送密码重置邮件
   - 要求下次登录时修改密码

3. 当平台管理员禁用租户管理员时，系统应：
   - 设置 `is_active` 为 false
   - 使所有活跃会话失效
   - 在重新启用前阻止登录

### REQ-8: 全局交易数据查询

**用户故事:** 作为平台管理员，我希望能够查看所有租户的交易用户产生的交易记录，以便进行全局数据分析和监控。

#### 验收标准

1. 当平台管理员查看全局交易统计时，系统应：
   - 显示全平台交易总量 (订单数、成交数)
   - 显示全平台交易总额
   - 支持按时间范围筛选 (今日、本周、本月、自定义)
   - 显示各租户交易量排名

2. 当平台管理员查看交易记录列表时，系统应：
   - 支持按租户、时间范围、交易品种筛选
   - 支持分页查询
   - 显示订单基本信息 (品种、方向、手数、盈亏)
   - 关联显示所属租户信息

3. 当平台管理员查看特定租户交易数据时，系统应：
   - 通过调用该租户中间件实例 API 获取数据
   - 显示该租户的交易用户列表及交易统计
   - 支持查看用户持仓和历史订单

4. 系统数据获取方式：
   - 交易数据存储在各租户的中间件数据库中
   - Platform Service 通过调用中间件 `/api/v1/trading/history/*` 和 `/api/v1/monitor/stats` API 获取数据
   - 支持聚合多个实例的数据进行全局统计

## 非功能性需求

### 代码架构与模块化

- **单一职责原则**:
  - 每个模块 (tenants, instances, invoices) 有独立的 service, controller, DTO
  - Prisma 服务隔离在专用模块中

- **模块化设计**:
  - NestJS 模块结构具有清晰边界
  - 共享工具在 common 模块中

- **依赖管理**:
  - 所有服务使用依赖注入
  - 避免模块间的循环依赖

- **清晰接口**:
  - 为所有 API 输入/输出定义 DTO
  - 使用 TypeScript 接口定义内部契约

### 性能

- 列表操作 API 响应时间 < 200ms (带分页)
- 单实体操作 API 响应时间 < 100ms
- 支持分页，每页最多 100 项
- 数据库查询应对常用筛选器 (tenant_id, status) 使用索引

### 安全性

- 所有 API 端点需要 JWT 认证
- 基于角色的访问控制 (平台管理员角色: super_admin, admin, operator)
- 使用 bcrypt 进行密码哈希，成本因子为 12
- 敏感数据 (passwords, api_keys) 永不在 API 响应中返回
- 所有状态变更操作的审计日志
- 限流: 每管理员每分钟 100 个请求

### 可靠性

- 多表操作使用数据库事务
- 使用标准化错误响应进行优雅的错误处理
- 用于监控的健康检查端点
- 瞬态故障 (数据库连接) 的自动重试

### 可用性

- 遵循 OpenAPI 3.0 规范的 RESTful API 设计
- 带错误码的一致错误响应格式
- 描述性字段验证消息
- 带示例的 API 文档
